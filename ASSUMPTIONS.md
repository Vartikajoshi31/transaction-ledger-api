# 📋 Architectural Decisions & Assumptions

This document outlines the key assumptions, domain modeling choices, and engineering decisions implemented in the **Transaction Ledger API**.

---

## 1. Account Identifier Strategy
- **Requirement:** `id must be unique... created_at should be generated by the system.`
- **Implementation:** Accounts and Transactions are assigned **UUID v4** strings upon creation.
- **Rationale:** UUID v4 provides globally unique, cryptographically random identifiers that prevent account enumeration vulnerabilities and support horizontal distribution across database shards without central counter collisions.

---

## 2. Initial Balance Policy
- **Requirement:** `Initial balance must always be 0. The client should not be allowed to set the initial balance.`
- **Implementation:** The request body schema for `POST /accounts` only permits the `name` field and is marked `.strict()`. Any client attempting to supply `balance` or `created_at` receives a `400 Bad Request (VALIDATION_ERROR)`. The system unconditionally initializes account balance to `0.00`.

---

## 3. Financial Precision & Floating-Point Protection
- **Domain Reality:** Financial calculations must never suffer from IEEE 754 binary floating-point rounding quirks (such as `0.1 + 0.2 = 0.30000000000000004`).
- **Implementation:**
  1. Input amounts must be positive numbers with **at most 2 decimal places** (cents). Floating numbers with excessive fractional precision (e.g., `10.555`) are rejected upfront by input validation.
  2. All internal calculations apply explicit rounding to 2 decimal places: `Math.round(val * 100) / 100`.
  3. The database enforces a strict `CHECK (balance >= 0)` constraint, acting as a secondary defense layer ensuring negative balances are impossible at the storage engine level.

---

## 4. Reference ID Scope & Duplicate Detection (Idempotency)
- **Requirement:** `For the same account, reference_id must be unique... The same reference_id may be used for different accounts.`
- **Implementation:**
  - A compound unique constraint `UNIQUE(account_id, reference_id)` is defined on the `transactions` table.
  - An atomic check occurs before insertion. If a transaction with the same `(account_id, reference_id)` exists:
    - No new transaction is written.
    - Account balance remains completely unchanged.
    - The API returns `409 Conflict` with error code `DUPLICATE_TRANSACTION`.
  - The same `reference_id` is fully permitted across different accounts, exactly as mandated.
  - Transfers also use a global unique `reference_id` on the `transfers` table to ensure transfer idempotency.

---

## 5. Atomicity & Concurrency Model
- **Requirement:** `Creating a transaction and updating the account balance must be treated as one atomic operation. If either operation fails, neither change should be persisted.`
- **Implementation:**
  - Every transaction (and transfer) is wrapped within `db.transaction(() => { ... })`.
  - In SQLite, this runs as `BEGIN IMMEDIATE` transaction, acquiring a reserved lock.
  - If any assertion fails (e.g. insufficient funds, duplicate reference, invalid account), an exception is thrown and the database automatically issues a `ROLLBACK`.
  - Concurrency tests demonstrate that simultaneous debit attempts safely serialize: only requests with sufficient available balance succeed, and the remaining requests are rejected with `422 INSUFFICIENT_BALANCE` without race conditions or negative balances.

---

## 6. Transaction Immutability & Audit Trail
- **Requirement:** `Once a transaction is created, it must not be editable or deletable through the API.`
- **Implementation:**
  - The API does not expose any `PUT`, `PATCH`, or `DELETE` endpoints for transactions.
  - Foreign key constraints use `ON DELETE RESTRICT` to prevent orphan records or cascade deletions.
  - Transactions serve as an append-only ledger of record.

---

## 7. Pagination & Sorting Semantics
- **Requirement:** `Transactions must be returned in latest-first order, based on created_at... Support pagination using parameters such as page, limit.`
- **Implementation:**
  - SQL query applies `ORDER BY created_at DESC, id DESC` to ensure deterministic, latest-first ordering even if timestamps coincide within the same millisecond.
  - Defaults: `page = 1`, `limit = 10`.
  - Pagination limits are bounded between 1 and 100 to protect server resources from unbounded memory allocation.
  - Responses provide `page`, `limit`, `total_records`, `total_pages`, as well as both `transactions` and `data` keys to ensure compatibility with various front-end frameworks.

---

## 8. Money Transfer Architecture (Bonus)
- **Requirement:** `Transfer money from one account to another atomically... A partial transfer must never be possible.`
- **Implementation:**
  - `POST /transfers` validates that `source_account_id !== destination_account_id`.
  - Inside a single atomic transaction:
    1. Verifies both source and destination accounts exist.
    2. Validates source account has sufficient balance (`source.balance >= amount`).
    3. Atomically debits source account and credits destination account.
    4. Creates 2 linked ledger transactions (debit on source, credit on destination).
    5. Writes an audit record to the `transfers` table linking both transaction IDs.
  - If any step fails, the entire transaction is rolled back; both account balances and transactions remain untouched.
